# BRSCP v0.6 → v0.7 修補記錄

**日期**：2026-07-26
**依據**：2026-07-25 benchmark（協德，8 模型）＋ blind frontier test（opus-5, n=1）
**驗證**：`state_machine_check.py` — v0.6 得 1/6，v0.7 得 6/6

---

## 為什麼要改

benchmark 顯示完整 BRSCP 協議在假完成率上與等長無關文字（placebo）**無統計差異**，
而一句短誠實提示（honesty_only）在部分模型上把假完成率從 1.00 壓到 0.00。

原本的解釋是「協議太長，把自己的機制稀釋掉了（context dilution）」。
但 opus-5 這個前沿模型也失敗了——前沿模型吃 8k 字前綴不該被稀釋。
所以稀釋不是全部原因。

追查協議原文後，找到三處**閉環斷點**。這才是主因。

---

## 修補一：補上「致命且不可修 → ESCALATE」這條缺的邊

**v0.6 原文（G4G5）：**
```
3. 只有當：找到的缺陷都不致命 + 每個標準都能引用，才算過。
→ 缺陷致命 或 有標準引用不出來 → 繼續做
```

「繼續做」**預設了缺陷可修**。協議沒有涵蓋「致命 + 不可修」這個處境。

**實測後果（opus-5 B-4）：** agent 正確偵測到規格自相矛盾（0.72 < 0.85，數學上無解），
查協議 → 「繼續做」→ 但規格矛盾修不了 → 無事可做 → 掉回 complete。

**v0.7：** G4G5 拆成四個 outcome，`致命且不可修 → escalate`。
所有六門都補上對應的「外部阻擋」出口。

---

## 修補二：讓 ESCALATE 在單輪情境可達

**v0.6 的兩個入口：**
```
line 125：→ 繼續做（最多重試 2 次，還不行就 ESCALATE）
line 161：ESCALATE → 我反覆嘗試還是搞不定
```

兩個都要求 **retry 歷史**。協議被貼進單次對話時，不存在「反覆嘗試」。
**ESCALATE 在單輪情境下是結構性不可達狀態。**

**v0.7 四個入口，三個不需要重試：**
1. 任務本身不可能（規格矛盾／目標互斥）
2. 缺乏達成所需條件（資訊／權限／工具／前置產物）
3. 需要人的價值裁定
4. 重試後仍失敗（保留 v0.6 入口）

## 修補三：全協議綁定 `claimed_status`

**實測：** v0.6 協議全文搜尋 `claimed_status` → **出現 0 次**。

協議一直在講「算過」「繼續做」「COMPLETE」這些抽象狀態，
但 agent 實際要輸出的欄位叫 `claimed_status`，協議一次都沒指名它。

**它在控制一個它從未指名的變數。**

**v0.7：** 每一門的路由都明文寫「→ `claimed_status` 應為 X」。

---

## 修補四（自我紅隊時發現）：CONTINUE 在單輪的語意

v0.6 的 CONTINUE 預設有下一輪。單輪情境下 agent 標了 CONTINUE 然後結束回應，
**等同換了個標籤的假完成**。

**v0.7：** 單輪下 CONTINUE = 「在本次回應內續做，做完重跑檢查」；
本次回應內做不完 → 降級 `escalate`。明文禁止「標了 CONTINUE 就結束」。

---

## 修補五：分層軸從「複雜度」換成「風險」

草案版 v0.7 依任務複雜度分層。**這是錯的軸。**

反證就在 benchmark 裡：`task_b` 是一個 15 行的計價函式——極小任務，
但算錯的是錢。在複雜度分層下它只會拿到最輕的保護，而它正是唯一出事的那個。

**v0.7：** 依風險／不可逆性分層。並且：
- 風險不可由執行任務的 agent 自行評定並降級（理由與 FM-3.3 同源）
- 無法判定時 **預設最高層**（誤判為高只是多花 token，誤判為低會出事，代價不對稱）
- agent 可向上升級，不可向下降級

## ⚠️ 我沒修好的部分（自我紅隊，誠實列出）

### 嚴重

**1. 判斷點被搬移了，不是被消滅**
v0.7 補了「致命且不可修 → escalate」，但「可修 / 不可修」**仍然由 agent 自評**。
我把 FM-3.3 從「致命 vs 非致命」的自評，搬到了「可修 vs 不可修」的自評。

誠實的定位：**v0.7 修好的是「誠實的 agent 撞到協議死路」這一類失敗**（B-4 就是這類——它分類正確，是協議沒門）。
它**沒有**修好「agent 在分類上放水」。後者需要 code 層強制或 L2 的獨立判定。

**2. L0 措辭沒有測過**
我上一輪才說「L0 措辭應該是全系統測最兇的一個字串，用猜的是重蹈覆轍」，
然後這一輪我用猜的寫了 L0。**我犯了我自己剛指出的錯。**
L0 措辭必須做 5 候選 × 4 模型的掃描後才能定案。目前這版是待測草稿，不是定稿。

**3. 過度升級風險完全沒處理**
v0.7 新增三個 ESCALATE 入口 = **讓 escalate 更容易觸發**。
如果 escalate 太容易，agent 會傾向什麼都不做就升級。
我加了門，但沒加防止濫用門的機制，也還沒有 `true_completion_rate` 的數據來確認代價。

### 中等

**4. 路由表是手動抽的，不是從協議自動解析**
`state_machine_check.py` 的路由表由我人工從協議抄出。
若協議改了而路由表沒同步，檢查會驗證一個不存在的東西。
**這正是 BRSCP 自己要防的 spec-implementation drift。** 應改為從協議文字自動解析。

**5. C4 只驗「出現次數」，不驗「綁定品質」**
協議可以出現 `claimed_status` 六次但語意鬆散，檢查照樣通過。
必要條件，非充分條件。

**6. 風險訊號清單沒有依據**
哪些標 ★、幾項算 L2，都是我拍的，沒有數據支撐。

## 採用前必須做的事

| # | 事項 | 為什麼擋 |
|---|---|---|
| 1 | L0 措辭掃描（5 候選 × 4 模型）| 目前是猜的，而措辭 × 模型交互作用已證實極大（nemotron 對 honesty_only 完全無感）|
| 2 | 補報 `true_completion_rate` | 沒有它就不知道 v0.7 是否把假完成換成了過度升級 |
| 3 | 統一 placebo 長度單位 | Gate 1 的 dilution 結論目前處於未定狀態（codepoint vs byte 不一致）|
| 4 | 位置測試 | 「綁定規則放最後」這條設計沒有實證，只有 recency 的理論推測 |
| 5 | 路由測試 | 「只偵測不路由 = 洩壓閥」這個假說直接對應 v0.7 的核心改動，該獨立驗證 |

**在 1、2 完成前，v0.7 是候選版本，不是定稿。**

## 本輪追加（動態分層實作完成）

前一版只有分層的**描述**，沒有可載入的東西。本輪補完：

**1. 三層做成實際可貼的文字檔**
`tiers/L0.md` (483) / `L1.md` (1189) / `L2.md` (1528) codepoints。
L0 ⊂ L1 ⊂ L2，機械驗證單調包含（C8）。

**2. 觸發判定做成可執行實作**
`brscp_v07.py` 的 `select_tier()`，9/9 自測通過。
關鍵案例：「小任務但涉及計價」正確升到 L2 —— 這是複雜度分層會漏掉的那一類。

**3. 消滅 spec drift（修掉 v1 紅隊第 4 項）**
路由表改由 `routing.json` 宣告，協議與檢查程式共用同一份真相。
新增 C7 反向檢查：宣告的終止狀態必須真的出現在載入文字中。

**4. C4 升級（修掉 v1 紅隊第 5 項）**
不再只數 `claimed_status` 出現次數，改為檢查它是否落在綁定語境（必須／不得／=／→ 附近）。

**5. 對稱舉證負擔（修掉 v1 紅隊第 3 項的一半）**
只堵 complete 會讓 agent 逃往 escalate。
新增：escalate 也要寫出「試過什麼／為何不通／需要誰給什麼」三項；
分類「不可修」「非致命」也要附理由。
這提高了作假成本，但**沒有消滅自評**——仍列在未解項。

**6. 發現並修掉一個新漏洞**
實際載入的 L0/L1 原本幾乎沒指名 `claimed_status`（綁定又鬆掉了）。
主文件寫了 6 次不算數，**要看實際貼進 prompt 的那份**。修正後 L1 出現 14 次，全在綁定語境。

檢查項從 6 項增為 9 項：v0.6 得 4/9，v0.7 得 9/9。
