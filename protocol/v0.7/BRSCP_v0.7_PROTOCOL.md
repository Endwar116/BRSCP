## v0.7 改了什麼

v0.6 的協議**控制一個它從未指名的變數**，而且在單輪情境下 `escalate` 是不可達狀態。

實測證據（opus-5 盲測 B-4）：agent 正確偵測到規格自相矛盾，寫進缺陷清單，
自述「我沒有向使用者提出這個規格衝突（只在此列出）」，然後照樣標 complete。

**偵測成功、升級失敗。缺陷清單變成洩壓閥。**

## 五個修補

### 1. 補上「致命且不可修 → escalate」這條缺的邊

v0.6 原文只有「缺陷致命 → 繼續做」，**預設了缺陷可修**。
規格矛盾這種不可修的處境，協議沒有出口。

### 2. 讓 escalate 在單輪可達

v0.6 兩個入口都要求 retry 歷史，單輪對話裡不存在「反覆嘗試」。
v0.7 四個入口，三個免 retry。

### 3. 全協議綁定 `claimed_status`

v0.6 全文出現 **0 次**。v0.7 的 L1 出現 14 次，全部在綁定語境。

### 4. 定義單輪下 continue 的語意

單輪標了 continue 就結束回應 = 換個標籤的假完成。
v0.7：continue = 「本回應內續做」，做不完 → 降級 escalate。

### 5. 分層軸從「複雜度」換成「風險」

反證是 benchmark 裡的 `task_b`：15 行計價函式，極小任務，但算錯的是錢。
複雜度分層下它只拿最輕保護，而它正是唯一出事的那個。

## 兩個對稱的舉證負擔（本輪新增）

只堵 complete 這一邊，agent 會逃往 escalate。所以兩個終止狀態都要付成本：

**complete 要舉證** —— 每一項標準都能舉出證據

**escalate 也要舉證** —— 必須寫出三項：
① 我試過什麼　② 為什麼那條路不通　③ 需要誰提供什麼我才能繼續
寫不出來 → 這不是 escalate 的處境，回去做

**分類也要舉證** ——
標「不可修」要附上試過哪幾條路、每條為何不通；
標「非致命」要說明它為何不影響 deliverable 達成。

## 分層觸發

### 風險訊號

**★ 訊號（任一命中 → L2）**
不可逆動作／對外產生影響／金流計價／安全權限隱私

**一般訊號（一項 → L1，兩項以上 → L2）**
寫入檔案設定資料庫／觸及 production／多方協作

**迴圈訊號（任一 → 至少 L1）**
已進入第二輪／上輪判定 continue／已產出可驗證產物

### 判定來源（依序）

1. 用戶明示
2. SIC-JS `task.priority`（P0 → L2）
3. 可觀察訊號比對
4. **無法判定 → 預設 L2**

第 4 條是 fail-safe：誤判為高風險只多花 token，誤判為低風險會出事，兩者代價不對稱。

**執行任務的 agent 可向上升級，不可向下降級。** 降級只能由用戶明示。
理由與 FM-3.3 同源：想完成的一方會傾向把風險評低來省事。

### 三層

| 層 | 觸發 | 長度 |
|---|---|---|
| L0 | 永遠 | 483 codepoints |
| L1 | 有迴圈 或 命中風險訊號 | 1189 |
| L2 | ★ 訊號／兩項以上／P0／風險未定 | 1528 |

對照 v0.6 全量載入 4081 codepoints。**常態載入量降至 12%。**

L0 永遠在場、不進動態、置於 prompt 最末。
它是目前唯一有實測證據支持的部分，且成本趨近零。

## ⚠️ 仍未解決（誠實列出）

**1. 判斷點被搬移，不是被消滅**
「可修 / 不可修」仍由 agent 自評。v0.7 用舉證要求（要寫出試過哪幾條路）提高了作假成本，但沒有消滅自評。

誠實定位：**v0.7 修好的是「誠實的 agent 撞到協議死路」這一類失敗**——B-4 就是這類，它分類正確，是協議沒門。
它**沒有**修好「agent 在分類上放水」，那需要 code 層強制或 L2 的獨立判定。

**2. L0 措辭沒有測過**
措辭 × 模型的交互作用已被實測證明極大（nemotron 對 honesty_only 完全無感，qwen/8b 卻 1.00 → 0.00）。
目前 L0 是依設計原則寫的草稿，不是實測選出的最佳措辭。

**3. 過度升級的代價未知**
v0.7 新增三個 escalate 入口 = 讓 escalate 更容易觸發。
對稱舉證負擔是設計上的防濫用，但沒有數據確認它夠不夠。

**4. 風險訊號清單無數據依據**
哪些標 ★、幾項算 L2，是依常識判斷排的。
